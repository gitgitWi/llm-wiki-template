# llm-wiki

# LLM Wiki (Karpathy)

이 문서는 LLM 에이전트(OpenAI Codex, Claude Code 등)를 활용해 **개인 지식 베이스를 지속적으로 축적·유지하는 위키**를 구축하는 패턴을 제안한 아이디어 파일입니다. 기존 RAG 방식이 질의 때마다 원본 문서에서 지식을 매번 재발견하는 데 그치는 한계를 지적하고, 대신 LLM이 원본과 사용자 사이에 **영구적·복합적으로 성장하는 위키**를 직접 작성·유지하는 구조로 전환하는 것이 핵심입니다.

**핵심 내용**

- 기존 RAG·NotebookLM·ChatGPT 파일 업로드는 질의 시점에 관련 청크를 검색해 답을 생성할 뿐 **지식이 축적되지 않는다.** 다섯 문서를 종합해야 하는 미묘한 질문도 매번 처음부터 조각을 찾아 맞춰야 한다.
- 제안된 구조는 질의 시점 검색 대신, 새 소스를 넣으면 LLM이 **읽고 핵심을 추출해 기존 위키에 통합**한다 — 엔티티 페이지 갱신, 주제 요약 수정, 기존 주장과 모순되는 새 데이터 표기, 종합 강화·도전. 지식은 "한 번 컴파일되어 계속 현재 상태로 유지"된다.
- **3계층 아키텍처**: ① 불변의 원본 소스(LLM은 읽기만 함, source of truth) ② LLM이 전적으로 소유하는 위키(마크다운 파일 디렉토리) ③ 스키마(CLAUDE.md/AGENTS.md)로 위키 구조·규칙·워크플로를 정의 — 이 파일이 LLM을 "훈련된 위키 관리자"로 만드는 핵심 설정.
- **세 가지 운영**: *Ingest*(소스 하나가 10~15개 위키 페이지에 영향, 한 번에 하나씩 처리 권장), *Query*(검색·종합·인용 후 **좋은 답변을 새 페이지로 위키에 다시 제출**해 탐구도 축적), *Lint*(모순·낡은 주장·고아 페이지·누락 크로스레퍼런스·데이터 공백을 주기적으로 점검).
- **특수 파일 두 개**: `index.md`는 콘텐츠 지향 카탈로그(페이지+요약+메타데이터)로 ~100개 소스·수백 페이지 규모에서 임베딩 RAG 인프라 없이 잘 동작하고, `log.md`는 연대순 append-only 기록으로 일관된 접두사(`## [2026-04-02] ingest | ...`)를 쓰면 `grep "^## \[" log.md | tail -5` 같은 유닉스 도구로 파싱 가능.
- **옵션 도구**: 규모가 커지면 `qmd`(마크다운 로컬 검색엔진, BM25+벡터 하이브리드 검색·LLM 재랭킹, CLI·MCP 서버 제공)를 추천하며, Obsidian Web Clipper, 이미지 로컬 다운로드, graph view, Marp, Dataview, git 버전 관리 등이 팁으로 제시됨.
- **왜 작동하는가**: 지식 베이스 유지의 진짜 병목은 읽기·사고가 아니라 **북키핑**(크로스레퍼런스 갱신, 요약 유지, 모순 표기)인데, 인간은 유지보수 부담이 가치를 앞지를 때 위키를 포기하지만 LLM은 지루해하지 않고 한 번에 15개 파일을 건드릴 수 있어 유지 비용이 거의 0이 된다. Vannevar Bush의 Memex(1945) 비전과 정신적으로 연결된다.

**결론**

LLM을 위키의 "프로그래머", Obsidian을 "IDE", 위키를 "코드베이스"로 삼아, 인간은 소싱·탐구·질문에 집중하고 LLM이 모든 정리·유지 노동을 담당하게 하는 패턴입니다. 문서는 의도적으로 추상적이며, 구체적 디렉토리 구조·스키마·도구는 사용자와 자신의 LLM 에이전트가 협력해 도메인에 맞게 인스턴스화하도록 설계되었습니다.
