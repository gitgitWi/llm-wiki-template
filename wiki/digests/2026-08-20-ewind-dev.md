# Effect 옹호론 — 부작용을 통제하면 시간까지 교체할 수 있다

> 중국어 X 포스트. `@ThaddeusJiang` 의 "이 프레임워크를 왜 좋아하는지 모르겠다" 는 질문에 대한 답글이다.
> 검증 결과는 [[effect-ts-dst-testing]] 에 있다.

## 글쓴이의 주장

**단점은 먼저 인정한다.** Effect 는 자기 방식(pipe·DI·`yield`)을 사실상 강요하고, Layer 개념은 난해하고, plain TypeScript 같지 않다. 최대 단점은 boilerplate 라서 사람이 손으로 쓰기 부담스럽다는 점이라고 못 박는다.

**대가로 얻는 것은 외부 세계의 교체 가능성이다.** 업무 로직의 부작용이 전부 Effect 로 통제되면, 프로그램이 의존하는 외부 세계를 갈아끼울 수 있다. 시간도 포함된다. 글쓴이는 네이티브 `setTimeout` 과 마이크로태스크 스케줄링이 시점을 통제 불가능하게 만드는 것이 E2E flakiness 의 뿌리라고 본다. 시간을 가상으로 다루면 수 분짜리 E2E 가 단위 테스트 수준으로 내려온다.

**이걸 DST 라고 부른다.** 최근 Ryan Dahl 이 celld 를 이야기할 때도 DST 에서 영감을 받았다고 언급했다고 인용한다.

**웹 앱이면 더 밀어붙일 수 있다.** 환경을 자유롭게 바꿔도 동형(isomorphic)이 유지된다면, 프론트와 백 로직을 한 프로세스의 가상 시계에서 함께 빨리 감을 수 있다. 최대 장벽은 Postgres 같은 DB 인데, PGlite 가 WASM 인프로세스 임베딩을 지원한다는 점을 든다.

**구체적 예시**: 위챗 같은 IM 을 만든다면, 프론트 데이터층은 SQLite, 백엔드는 PG 로 두고 한 Node 프로세스 안에서 "PG 초기화 → 그룹방에서 A 가 메시지 전송 → 철회 → B 접속 후 수신 → SQLite 반영" 같은 복잡한 시퀀스를 TestClock 하나로 결정적으로 모델링해 가속 실행한다.

**테스트 입도**: 필드 세부를 검증하지 않고 사용자가 최종적으로 보는 내용만 검증하는 BDD 스타일. AI 를 두고 두더지잡기 하는 상황을 피하는 데 유용하다고 본다.

**마무리 논지**: boilerplate 가 최대 단점이지만, 앞으로 사람이 정말 손으로 코드를 써야 하는가?

## 내가 쓸 수 있는 지점

- "시간을 의존성으로 취급하라" 는 통찰은 Effect 도입과 분리해서 가져올 수 있다.
- 반대로 "가상 시계 = DST" 등식과 "인프로세스 풀스택 = E2E" 등식은 각각 과장이다. 근거는 [[effect-ts-dst-testing]] §6·§7.
- 결론부의 AI 논지는 [[agentic-coding-design-and-code-review]] 의 "작성은 싸졌지만 이해는 비싸다" 와 정면으로 맞물린다.
