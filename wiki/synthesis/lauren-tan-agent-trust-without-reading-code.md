# Lauren Tan — 에이전트 코드를 안 보고도 믿는 시스템

> 2026-08-30 정리. Cursor의 Lauren Tan(트위터 Potato, 전 Meta React Compiler / Netflix EM) 강연을 자동생성 자막 기준으로 재작성했다. 고유명사는 자막 오기를 문맥으로 교정했다(Grokbot/Rockbot → Grok Bot, Glass → Agent Window 코드명, PStack/PSAT → PStack, Claudians → cloud agents, email playbook → eval playbook, Bogbot → Bugbot). 수치·제품 주장은 강연자 발언이며 독립 검증하지 않았다.

핵심 주장: **코드를 안 봐도 되는 상태**는 에이전트를 더 많이 돌린 결과가 아니라, **검증 루프·스킬·하드 가드레일**로 신뢰를 쌓은 뒤에야 성립한다. 사람이 verifier로 남는 한 병렬화도 auto-merge도 없다. 같은 축의 다른 정리: [[agentic-coding-design-and-code-review]].

---

## 신뢰가 스케일의 전제다

**주장.** 에이전트를 못 믿으면 사람은 병목이고, 하나를 못 믿으면 백 개를 띄울 수 없다.

**이유.** 엔지니어는 에이전트가 자신 있게 틀린 원인을 말할 때마다 신뢰를 잃는다. 그때의 운영 모드는 매니저의 마이크로매니지먼트와 같다 — 어깨 너머로 출력을 전부 본다.

**근거.** 강연자는 에이전트 코딩을 EM 스킬과 평행하게 본다. 초기는 “한 줌의 에이전트를 in-the-loop로 보고 프롬프트하는” 구간이다. Cursor 합류 직후 Agent Window 성능 작업에서 본인이 트레이스를 찍어 넘기는 동안 에이전트는 틀린 smoking gun을 반복했다. 그가 그린 신뢰 곡선은 기여량과 역으로 맞물린다고 한다: 합류 5개월, 전월 약 1000 PR, 그달 12일 기준 약 800 PR(본인 주장). 당일 아침에는 에이전트가 auto-merge한 PR 약 20개를 이미 랜딩된 main에서 사후 리뷰했다고 한다.

---

## 먼저 닫을 루프는 “좋은 코드”가 아니라 “맞는 코드”

**주장.** 에이전트와 일할 때 툴박스의 1순위는 **verification** — 에이전트가 실제 앱을 사용자와 같은 경로로 돌려 스스로 확인하는 능력이다.

**이유.** 검증은 품질을 보장하지 않지만 **올바른 동작**까지 루프를 닫는다. 사람이 로컬 빌드를 열고 스크린샷·콘솔을 붙여 넣는 한, 그 사람이 병목이다.

**근거.** CPU 트레이스, 힙 스냅샷, iOS 시뮬레이터, Chrome DevTools Protocol. Cursor에서 그가 만든 첫 스킬이 Agent Window 제어용 **Control Glass**(내부 코드명 Glass)다. Electron·웹·iOS라면 CDP·시뮬레이터 제어를 가르치면 비슷한 스킬을 만들 수 있다고 한다.

---

## 앱을 띄울 줄 알아도, 어디를 클릭할지 모르면 검증은 무용하다

**주장.** 검증 스킬에는 **feature map**(기능 → UI 경로·단축키·CDP 셀렉터)이 붙어야 한다.

**이유.** 에이전트는 앱을 띄워도 “사이드바가 끊긴다”, “PR 탭이 안 된다”에서 코드·화면 위치를 헤맨다. 저품질 리포트(스크린샷과 물음표)는 맵 없이는 매핑이 안 된다.

**근거.** 내부 Slack의 Agent Window / Grok Bot 피드백이 그 예. PStack의 `create verification skill` / `maintain verification skill`이 코드베이스를 탐색해 맵을 만들고 갱신한다. PStack(Potato Stack)은 YC Gary Tan의 GStack을 빗댄 플러그인으로, Control Glass부터 관측된 실패 모드를 스킬로 쌓아 자랐다.

---

## 스킬은 실패 모드의 누적이고, 충분함은 eval로 잰다

**주장.** 스킬은 철학 문서가 아니라, 툴콜을 읽고 잡은 실패를 마크다운 절차로 고정한 것이다. 수정 후에는 **에이전트용 유닛테스트(eval)** 없이 유지하지 않는다.

**이유.** 코딩은 잘해도 맥락 없이 추측하는 에이전트는 신입과 같다. 앞 토큰이 좋으면 더 나은 패턴을 탄다. 제품이 바뀌면 스킬은 낡고, 에이전트는 eval인 줄 알면 행동을 바꾼다.

**근거.** 초기에 관련 코드를 안 읽고 원인만 단정하는 환각을 툴콜에서 봤다. 그때마다 “찾아라 / 서브에이전트를 써라 / 추측하지 마라”를 붙였다. PStack Potato Mode의 eval playbook: 코디네이터가 루브릭을 만들고, 평가 중임을 숨긴 디렉터리에서 서브에이전트를 돌리며, 다른 모델 judge로 교차검증한다. Cursor의 모델 매트릭스로 쓰는 모델을 eval한다. `/loop`로 점수를 hill-climb할 수 있고, Control Glass CLI도 같은 방식으로 올렸다. 유지에는 페어 프로그래밍식 **백시트 드라이버**(툴콜·thinking을 읽는 취향)가 필요하다고 한다.

---

## 로컬에서 믿은 뒤에만 클라우드가 배당이 된다

**주장.** 검증 스킬의 시작은 로컬이다. 신뢰가 생긴 뒤에 같은 스킬을 클라우드에 심으면 개인이 아니라 팀·회사가 레벨업한다. 못 믿은 채 수백 클라우드 에이전트를 띄우면 토큰만 태운다.

**이유.** 로컬에서는 에이전트–앱 상호작용을 사람이 볼 수 있다. 클라우드에서는 버그 리포트 같은 시그널을 에이전트가 집어 재현·PR까지 간다.

**근거.** **Benny**는 버그 리포트를 받아 클라우드 데스크톱에서 Cursor를 켜고 같은 Control 스킬로 재현한다. 어떤 건 “이미 main에 고쳐져 있으니 빌드만 내면 된다”까지 알려 준다. 여정 요약: 소수 에이전트 전수 관찰 → 로컬 검증 → 클라우드가 시그널을 집어 PR → (그가 도달한) auto-merge 후 main 사후 리뷰. PStack을 맹신하지 말고 포크해서 자기 엔지니어링 기준을 넣으라고 한다. 지름길은 없다고 강조한다.

---

## 코드를 안 보는 조건은 “최단 경로 = 올바른 경로”

**주장.** 사람이 PR을 안 읽는 것은 방치가 아니라, 에이전트가 편법으로 풀어도 그게 곧 올바른 방법이 되도록 아키텍처를 바꿔 둔 결과다.

**이유.** 가드레일 없는 바이브 코딩은 단기 편법으로 코드가 spiral한다(그가 말한 organic architecture 문제). 빅테크 인프라(컨벤션, 프레임워크, 자격 제한)는 원래 “가장 약한 엔지니어”를 전제로 했고, 그게 에이전트에도 맞다. 브라운필드는 가드레일이 있으면 에이전트가 일을 잘하고, 그린필드는 기회이자 최대 리스크다.

**근거.** Grok Bot은 프로토타입으로 빠르게 바이브 코딩됐고 사람은 코드를 거의 안 읽었다. 이후 **600개 넘는 PR**로 **Dune**(Electron용 Next.js 같은, 에이전트 작성용 아키텍처)으로 리팩터한 뒤에야 “코드를 거의 안 본다”, 디자이너·PM·GTM이 기능을 넣어도 밤중에 perf 회귀를 덜 걱정한다고 한다. CI가 빡세서 사람이 짜면 짜증나지만 그 짜증은 에이전트가 흡수한다. 원칙: **가장 둔한 에이전트도 생각 없이 맞게**, feature / entry point / transcript card 같은 명사와 **기능당 단일 디렉터리**로 80% 작업을 캡슐화.

---

## 강제력은 계층화하되, 돈은 하드 제약에 쓴다

**주장.** 리뷰 코멘트·스타일 가이드·스킬만으로는 코드베이스가 무너진다. 사람이 매번 지적하는 불변식은 린트 / CI 실패 / **문제 자체의 소거**로 올려야 한다. 코드 리뷰로 불변식을 지키는 상태를 안티패턴으로 본다.

**이유.** 에이전트는 규칙을 잊고 기존 패턴을 복사한다. 소프트 레이어(스킬, Bugbot, 에이전트 MD)는 겹쳐 두되 유일한 강제력으로 두지 않는다.

**근거 (Dune / Grok Bot, 강연 주장).**

- `useEffect` 등 React 풋건을 CI가 막음
- 코드 주석 금지 — 에이전트가 일시적 리뷰 멘트를 영구 규칙처럼 남김
- `electron-main` / `electron-renderer` 분리와 import 그래프 CI — 렌더러에 무거운 코드가 섞여 16ms/프레임을 깨는 패턴을 하드 페일
- 정적분석·컴파일러 진단이 하드, Bugbot·스킬은 소프트
- Agent Window는 아직 이 구조가 없어 PR마다 성능·안정성 회귀가 쉽다고 하며, 학습을 그쪽 리팩터에 가져갈 계획
- Rust처럼 컴파일러가 엄하면(unsafe만 막으면) 사람이 안 봐도 된다는 비유

PR 크기 상한은 없지만, 깃 히스토리와 revert를 위해 일을 여러 PR로 쪼개게 한다. 대략 수십~천 줄 편차.

---

## 토큰은 무한 전제가 아니지만, 프레임은 인프라 투자다

**주장.** 그가 한 방식 그대로는 일반 쿼터가 아닐 수 있다. 선행 토큰은 혼자 수년 걸릴 제약·리팩터를 사는 비용으로 본다.

**이유.** 에이전트 가치는 소소한 자동완성이 아니라, 예전엔 못 하던 수준의 제약을 코드베이스에 심는 것이다. 그 지점에 오면 “별로 안 똑똑한” 에이전트도 잘 짠다. 스타트업 리더 관점은 사람 고용 vs 토큰으로 가드레일 설치.

**근거.** Cursor는 토큰이 사실상 무제한이라고 본인이 인정. Grok 4.6은 4.5와 비슷한 토큰 단가에 지능을 올리는 Pareto를 강조(발표 시점 주장).

---

## Grok Bot은 같은 제약을 비개발자에게 열어 주는 면

**주장.** IDE / CLI / Agent Window는 파워유저용이고, Grok Bot은 에이전트에 이름·역할을 주고 오케스트레이션하는 **비개발자용 Cursor 모멘트**다(호스트 표현: Agents for Everyone).

**이유.** 배포 속도가 엔지니어 군대 수준이면 프로덕트도 따라가야 한다. Dune이 버티면 PM이 고친 버그 PR에 스탬프만 찍을 수 있다.

**근거.** iMessage 같은 인터페이스, 계정별 에이전트, “Lauren이 밤에 한 일 요약” 에이전트, 디자이너·PM이 기능을 직접 넣는 사례를 들었다.

---

## 한 줄

코드를 안 보고 믿는 시스템은 **(1) 실제 앱으로 닫는 검증 + feature map, (2) 실패 모드를 스킬·eval로 고정, (3) 최단 경로가 올바른 경로가 되게 하는 하드 CI/아키텍처**를 쌓아 신뢰 곡선을 오른 뒤에야 클라우드·auto-merge가 성립한다는 주장이다.
