# YAML vs TOML — 설정 파일 포맷 비교

> 2026-08-18 질문·정리. 두 포맷 모두 키-값 구조를 표현하지만 문법과 설계 철학이 다르다.

---

## 한눈에 보기

|| 축 | YAML | TOML |
|---|---|---|---|
| **전체 이름** | YAML Ain't Markup Language (재귀적) | Tom's Obvious, Minimal Language |
| **설계 목표** | 인간이 읽기 쉬운 데이터 직렬화 (계층·유연성) | 설정을 위한 최소·명시적 포맷 (모호함 제거) |
| **섹션 구분** | 들여쓰기로 암시 (체감 구조) | 명시적 `[section]` / `[[array-of-table]]` 헤더 |
| **키-값 문법** | `key: value` (들여쓰기 기반 중첩) | `key = value` (평평한 키, 헤더로 묶음) |
| **들여쓰기** | **의미 있음** — 스페이스로만, 탭 불가 | **의미 없음** — 오로지 가독성용 |
| **타입 추론** | 암묵적: `true`/yes/On → bool, 인용 없는 값은 스칼라 | 명시적: 문자열은 항상 인용(`"`) 필요, bool·int·float·리터럴 명확 |
| **주석** | `#` (줄 전체) | `#` (줄 전체) |
| **매크로/앵커** | `&anchor`, `*alias`, `<<: merge` — 복제·병합 가능 | 없음 (다만 `include` 등 상위 레이어가 별도) |
| **순환 참조** | 가능 (앵커 남용 시) | 불가 (트리 구조만) |
| **주요 사용처** | Kubernetes, GitHub Actions, gh-pages 설정, 마크다운 frontmatter, CI/CD | Rust(Cargo.toml), Python(pyproject.toml, Poetry), Rust/JS 생태계 설정 |

## 문법 차이 (구체 예시)

### 섹션/그룹핑

```yaml
# YAML — 들여쓰기가 곧 구조
server:
  host: 0.0.0.0
  port: 8080
database:
  url: postgres://...
  pool:
    min: 2
    max: 10
```

```toml
# TOML — [section] 헤더가 그룹을 명시
[server]
host = "0.0.0.0"
port = 8080

[database]
url = "postgres://..."

[database.pool]
min = 2
max = 10
```

**차이점**: YAML은 들여쓰기 깊이가 계층을 결정하고, TOML은 `[section]` / `[section.subsection]` 이 계층을 결정한다. TOML 쪽이 "어디부터 어디가 한 블록인지" 파싱 이전이라도 눈으로 읽기 쉽다.

### 배열·테이블 배열

```yaml
# YAML — 대시 리스트로 간결
items:
  - name: foo
    value: 1
  - name: bar
    value: 2
```

```toml
# TOML — [[array-of-tables]] 헤더가 반복 블록 명시
[[items]]
name = "foo"
value = 1

[[items]]
name = "bar"
value = 2
```

**차이점**: TOML의 `[[...]]` 는 "이 섹션이 배열 속 객체"라는 점을 명시적으로 선언한다. YAML은 대시 하나로 암시한다. **복잡한 반복 구조**에서 TOML 쪽이 의도치 않은 들여쓰기 실수에 덜 취약하다.

### 인용 규칙

```yaml
# YAML — 인용은 선택, 하지만 모호함 발생 가능
title: LLM Wiki             # 문자열
count: 42                   # 정수
flag: true                  # 부울
yes-value: yes              # ⚠️ 이것도 bool (true로 파싱됨)
```

```toml
# TOML — 문자열은 항상 인용, 타입 명료
title = "LLM Wiki"
count = 42
flag = true
yes-value = "yes"           # 문자열 원하면 반드시 인용
```

**차이점**: YAML은 짧게 쓰려다 타입 추론에 끌려갈 수 있다(`yes`, `no`, `on`, `off` 가 bool로 해석됨). TOML은 문자열 인용이 강제라서 타입 충돌이 적다.

### 앵커/별칭 (YAML 고유)

```yaml
defaults: &defaults
  timeout: 30
  retries: 3

service-a:
  <<: *defaults
  host: a.example.com
```

TOML에는 이런 복제·병합 메커니즘이 없다. 중복을 줄이거나 외부 레이어(빌드 툴, 전처리)로 처리한다.

## 철학 차이

### YAML: "사람이 읽고 쓰기 쉬운, 표현력 높은 직렬화"

- **장점**: 간결함, 중첩 표현의 부드러움, 앵커/병합으로 반복 줄이기, JSON-superset적 유연함.
- **단점**: 들여쓰기가 곧 문법이라 실수(스페이스/탭 혼용, 깊이 착각)가 파싱 오류로 직결됨. 타입 추론이 자명하지 않은 케이스가 있음. 스펙이 역사적으로 복잡(1.1 vs 1.2 차이, 다중 문서 `---`, 태그・サンプル 확장).
- **성향**: "조금만 써도 바로 이해됨" + "깊게 들어가면 함정이 많음". 대규모 문서·계층형 데이터 교환에 강점.

### TOML: "설정 파일은 한눈에 구조가 보여야 한다"

- **장점**: `[section]` 으로 구조 시각화가 즉각적, 들여쓰기 자유도 높아 정렬·가독성 편집이 편함, 타입 규칙이 명료(문자열은 인용 필수), "의도치 않은 파싱"의 여지가 적음. 파싱 구현이 단순하고 결정론적.
- **단점**: 반복 구조가 `[[...]]` 로 길어지고, 앵커/병합이 없어 중복을 줄이려면 상위 도구가 필요, 계층이 깊어질수록 `[a.b.c.d]` 경로가 길어질 수 있음. 값이 계속 `" "` 로 감겨 가독성 손실이 느껴질 수 있음.
- **성향**: "설정(canonical config)"에 특화. 지문처럼 읽히며, "애매함"을 줄이는 데 초점.

## AI가 볼 때: 어떤 포맷이 더 이해하기 쉬운가

**요약: 둘 다 잘 파싱하지만, TOML이 "의도"를 읽기 쉽고, YAML이 "암시된 구조"를 읽는 데 조금 더 맥락이 필요하다.**

- **LLM 파싱 관점**: YAML은 들여쓰기로 암시된 계층이라, 토큰 스트림에서 계층 경계를 문맥으로 추론해야 하는 순간들이 있다. TOML은 `[section]` / `[[...]]` 헤더가 계층을 직접 선언하므로 **구조 이해에 필요한 단서가 더 명시적**이다.
- **타입 모호성**: YAML의 `yes`/`no`/`on`/`off`·인용 없는 숫자·스칼라 자동 판정은 문맥에 따라 의도가 달라질 수 있다. TOML은 문자열 인용이 강제라서 **"이 값은 문자열"인지 "숫자/bool"인지** 토큰 수준에서 더 분명하다.
- **많이 학습된 포맷**: YAML은 CI/CD·Kubernetes·GitHub Actions·마크다운 frontmatter 등 학습 데이터가 광범위해, 일반적인 YAML 스니펫은 모델이 잘 다룬다. TOML도 Cargo·pyproject 생태계로 충분히 학습되어 있다.
- **실무 감각**: 짧은 설정(10~30줄)은 둘 다 문제 없다. 중간 규모 이상의 계층·반복이 섞이면 **TOML의 명시적 헤더가 파싱·생성 모두에서 덜 헷갈린다**는 경향이 있다(앵커·병합 복잡한 YAML은 예외).

**결론**: "AI가 이해하기 쉬운 쪽"은 TOML이 약간 유리하다(명시적 구조 + 타입 규칙). 다만 YAML은 학습량과 사용처가 넓어 실제 오류 빈도는 비슷하거나 상황에 따라 다를 수 있다.

## 토큰 절약 측면

### 일반적으로 TOML이 더 짧거나 비슷한 경우가 많다

|| 시나리오 | YAML | TOML | 토큰 비교 |
|---|---|---|---|---|
| 평평한 키-값 20개 | `key: value` ×20 | `key = value` ×20 | 거의 동등 (`:` vs `=`, 인용 요구 차이) |
| 중첩 3단계, 30줄 | 들여쓰기 + `:` — 줄마다 키 중복 적음 | `[a.b.c]` 섹션 헤더와 각 줄 `key =` | YAML이 약간 짧을 수 있음 (키 반복 ↓) |
| 반복 테이블(N개) | `- key: val` 대시 리스트 — 간결 | `[[section]]` 헤더 반복 (각 블록마다) | **YAML이 더 짧음** (대시 하나로 객체 시작) |
| 문자열 많음 | 인용 선택 가능 | 문자열 인용 강제 | **TOML이 더 길다** (`"..."`) |
| 주석·빈 줄로 가독성 확보 | 가능 | 가능 (들여쓰기 자유) | 비슷 |

### 종합

- **짧은 평문 설정**: 둘이 비슷.
- **반복 객체 배열(N개)**: YAML 대시 구문이 더 간결 → YAML 유리.
- **문자열이 주된 값**: TOML은 인용 필수 → TOML이 더 길어짐.
- **중첩이 깊고 키 repetition이 많은 경우**: TOML 섹션 헤더가 중복을 줄여줄 수 있지만, `[a.b.c.d]` 경로가 길어지면 또 다른 중복이 생김.
- **실무 결론**: 포맷 선택으로 토큰이 크게 갈리는 케이스는 드물다. **구조 설계(중복 줄이기, 플랫하게 만들기)가 포맷 선택보다 영향이 크다.**

## 언제 뭘 고를까

|| 상황 | 추천 | 이유 |
|---|---|---|---|
| 이미 생태계가 YAML로 고정된 도구(K8s, GitHub Actions, 많은 CI) | YAML | 도구 요구 사항 |
| Rust/Python 생태계 설정(Cargo, pyproject, Poetry) | TOML | 표준 |
| 마크다운 frontmatter (메타데이터 얇은 층) | YAML | 관례, 짧은 키-값에 적합 |
| 복잡한 반복 테이블 + 사람이 자주 편집 | TOML | `[[...]]` 명시성, 들여쓰기 자유 |
| 앵벌·병합으로 반복을 줄여야 하는 큰 문서 | YAML | `&/*/<<:` 기능 |
| 모호함 최소화가 중요한 설정(canonical config) | TOML | 타입 규칙 명확, 파싱 예측 쉬움 |
| 최소한의 토큰으로 많은 키-값 | 상황에 따라 | 스트링 적으면 TOML, 배열 많으면 YAML |
| 사람이 읽고 구조를 한눈에 파악해야 함 | TOML | 섹션 헤더 투명성 |

## 부록: 공통 함정

- **YAML 탭 금지**: 스페이스만. 탭 섞이면 파싱 오류.
- **YAML 다중 문서**: `---`/`...` 로 여러 문서 구분 — 단일 설정 파일에서 의도치 않게 나올 수 있음.
- **TOML 문자열 인용**: `" "` 가 기본, `' '` 리터럴은 거의 안 씀(이스케이프 규칙 다름). 문자열 원하면 반드시 `"`.
- **TOML 비벽면 배열**: 배열은 테이블 안에만. 최상위 배열-of-table은 `[[...]]` 로 선언.
- **두 포맷 모두 JSON으로 변환 가능**: YAML ⊂ JSON은 아님(순환·앵커 제외 시), TOML → JSON 변환은 명확.
