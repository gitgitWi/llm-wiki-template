# LLM Wiki 리서치: 방법론·툴 비교와 개인 문서 정리 설계

> 목적: 각 방법론/툴의 장단점 비교 → 장점 취합 → 개인 문서 정리 방식 설계

## 1. Karpathy LLM Wiki 요약

### 핵심 아이디어
- 기존 RAG(NotebookLM, ChatGPT 업로드 등)는 **쿼리 시점에 매번 원본에서 지식을 다시 찾아냄**. 축적(accumulation)이 없음.
- LLM Wiki는 **persistent wiki(영속적 위키)** 를 LLM이 **증분적으로 구축·유지**함. 원본 소스와 사용자 사이에 "구조화·상호연결된 마크다운 파일 모음"을 만듦.
- 새 소스를 넣으면 LLM이 읽고 → 핵심 추출 → 기존 위키에 통합(엔티티 페이지 갱신, 주제 요약 수정, 모순 표시, 종합 강화).
- 핵심 차이: **지식은 한 번 컴파일되고 계속 현재 상태로 유지**됨. 매 쿼리마다 재생성되지 않음. **복리(compounding) 효과**가 나는 지속적 산출물.
- 사용자가 위키를 직접 쓰지 않고, **LLM이 전부 작성·유지**. 사용자는 소싱·탐색·질문을 담당.
- 실제 활용 예: 한쪽에 LLM 에이전트, 다른 쪽에 **Obsidian**을 띄우고 실시간으로 결과를 탐색. "Obsidian은 IDE, LLM은 프로그래머, 위키는 코드베이스."

### 3계층 아키텍처
1. **Raw sources(원시 소스)**: 기사·논문·이미지·데이터 파일. **불변**(immutable) — LLM이 읽기만 하고 절대 수정 안 함. 진실의 원천(source of truth).
2. **The wiki(위키)**: LLM이 생성한 마크다운 파일 디렉토리. 요약·엔티티 페이지·개념 페이지·비교·개요·종합. LLM이 전적으로 소유.
3. **The schema(스키마)**: LLM에게 위키 구조·규칙·워크플로우를 알려주는 문서(Claude의 CLAUDE.md, Codex의 AGENTS.md). **핵심 설정 파일** — 일반 챗봇이 아닌 "훈련된 위키 관리자"로 만드는 장치. 사용자와 LLM이 함께 진화시킴.

### 주요 연산(Operations)
- **Ingest(섭취)**: 새 소스를 raw에 넣고 LLM이 처리. 읽기 → 요약 페이지 작성 → index 갱신 → 관련 엔티티·개념 페이지 갱신 → 로그에 추가. 소스 1개가 위키 10~15개 페이지를 건드림.
- **Query(질의)**: 위키에 대해 질문. 관련 페이지 검색 → 읽기 → 인용 포함 답변 합성. 답 형태: 마크다운 페이지/비교표/슬라이드(Marp)/차트(matplotlib)/canvas.
  - 핵심 통찰: **"좋은 답변은 새 페이지로 위키에 다시 저장"** 됨. 탐색(exploration)이 대화 기록에 사라지지 않고 지식베이스에 축적됨.
- **Lint(점검)**: 주기적으로 위키 건강검진. 페이지 간 모순, 낡은 주장, 고아 페이지(인바운드 링크 없음), 페이지 없는 중요 개념, 누락된 크로스레퍼런스, 웹 검색으로 채울 데이터 갭 등 확인. LLM이 새 질문·새 소스 추천.

### 인덱싱/로깅 2개 특수 파일
- **index.md**(내용 중심): 위키 전체 카탈로그. 각 페이지 링크·한 줄 요약·메타데이터(날짜·소스 수). 카테고리별(엔티티/개념/소스) 정리. 모든 ingest마다 갱신. 질의 시 index 먼저 읽고 관련 페이지 드릴다운. **중간 규모(~100소스, 수백 페이지)에서 임베딩 RAG 인프라 없이도 잘 동작**.
- **log.md**(시간순): append-only 이벤트 기록(ingest/query/lint). 일관된 접두사(예: `## [2026-04-02] ingest | Article Title`) 쓰면 유닉스 도구로 파싱 가능(예: `grep "^## \[" log.md | tail -5`).

### 팁
- **Obsidian Web Clipper**(브라우저 확장)로 웹 기사를 마크다운으로 변환해 raw에 넣기.
- 이미지를 로컬로 다운로드(Attachment folder path 고정 + Ctrl+Shift+D 핫키). LLM은 inline 이미지를 한 번에 못 읽으므로 텍스트 먼저 읽고 이미지 따로 봐야 함.
- **graph view**로 위키 모양 확인(허브/고아 페이지).
- **Marp**(마크다운 슬라이드)로 프레젠테이션 생성.
- **Dataview**(frontmatter 쿼리 플러그인): YAML frontmatter에 태그·날짜·소스 수 추가하면 동적 테이블 생성.
- 위키는 **그냥 git repo** — 버전 관리·브랜칭·협업 공짜.

### 왜 효과적인가
- 지식베이스 유지의 지루한 부분은 **북키핑(크로스레퍼런스 갱신, 요약 유지, 모순 표시, 수십 페이지 일관성)**. 인간은 이 부담 때문에 위키를 포기하지만 LLM은 지루해하지 않고 15개 파일을 한 번에 건드림. **유지비용 ~0 → 위키가 계속 관리됨**.
- 인간: 소스 큐레이션, 분석 방향, 좋은 질문, 의미 해석. LLM: 그 외 전부.
- 정신적 선조: **Vannevar Bush의 Memex(1945)** — 개인·큐레이션된 지식 저장소, 문서 간 연관 경로(associative trails). Bush가 못 푼 "누가 유지하나"를 LLM이 해결.

## 2. 유사/관련 방법론 (전통적)

### 2-1. Memex (Vannevar Bush, 1945)
- 개념: 모든 개인 기록을 마이크로필름으로 저장하고, 문서 간 **associative trails(연관 경로)** 를 만들어 탐색하는 개인 지식 기계.
- 장점: 개인 중심, 문서 간 연결의 가치 강조. LLM Wiki의 직접적 정신적 선조.
- 단점: 당시엔 유지 수단이 없어 구현 불가. "누가 링크를 관리하나" 문제.

### 2-2. Zettelkasten (Niklas Luhmann)
- 슬립박스(slip box) 메모법. 각 메모(원자적 아이디어)에 번호·태그·크로스레퍼런스로 연결. 9만 장 이상의 카드로 70권+ 저술.
- 핵심 원칙:
  - **원자성(atomicity)**: 메모 하나 = 하나의 아이디어.
  - **자기 자신의 언어로 재작성**(주석·복붙이 아니라).
  - **연결 중심**: 폴더 계층(카테고리)보다 메모 간 링크로 구조 형성.
  - **바텀업**: 처음부터 완성된 구조를 설계하지 않고 성장시킴.
- 장점: 지식 간 예상치 못한 연결 발견, 창의성, 축적 효과. LLM Wiki의 "상호연결된 마크다운"과 철학이 겹침.
- 단점: 규율 요구(원자성·자기 언어 유지), 초기 진입장벽, 수동 유지 부담 — **정확히 LLM Wiki가 자동화하는 바로 그 부담**.

### 2-3. 그래프 기반 PKM 도구 (Obsidian, Roam, Logseq)
- 위키/양방향 링크(bidirectional link) 기반 노트. Obsidian은 로컬 마크다운, graph view.
- 장점: 링크 기반 탐색, 확장 가능, 데이터 소유권(로컬 파일).
- 단점: 링크·요약·유지의 **부지런함이 수동적으로 사용자에게 요구**됨 → LLM Wiki가 이걸 대체.

### 2-4. 정보 조직 체계: PARA / Johnny.Decimal
- **PARA (Tiago Forte)**: Projects / Areas / Resources / Archives. 목적(actionability) 중심 4개 최상위 폴더.
- **Johnny.Decimal**: 모든 것을 10-99 숫자 네임스페이스로 분류(ID 부여). 위치가 곧 의미.
- 장점: 파일 배치 결정을 단순화. 사람이 "어디에 넣을까" 고민을 줄임.
- 단점: **계층(폴더) 기반**이라 교차 연결·재조직이 어려움. 지식의 연결적 성격과 잘 안 맞음. LLM Wiki는 이것을 링크 기반으로 보완.

## 3. 유사/관련 툴 (LLM 기반)

### 3-1. NotebookLM / Gemini Notebook (Google)
- RAG 기반: 소스 업로드 → 생성 시 관련 청크 검색 → 답변. Audio Overview(팟캐스트형 요약), Video Overview, 슬라이드·다이어그램·플래시카드 생성.
- 장점: 사용성, 진입장벽 낮음, 멀티모달(오디오·영상) 출력.
- 단점: **Karpathy가 지적한 핵심 한계** — 매 질의마다 재발견, **지식 축적 없음**, 소스는 클라우드에, 참조 연결 그래프가 지속성 있게 자라지 않음.

### 3-2. Mem0 (Universal memory layer for AI Agents)
- LLM 앱에 "메모리"를 추가하는 레이어. 대화/상태에서 관련 메모 검색 → 답변에 주입 → 새 메모 저장.
- 장점: 토큰 효율 메모리 알고리즘, 하이브리드 검색(시맨틱+키워드+엔티티 부스팅), 다양한 LLM 지원, 라이브러리/에이전트 통합.
- 단점: **런타임 메모리** 중심(에이전트의 맥락 보강) — 인간이 읽고 편집할 수 있는 **영속 문서 형태가 아님**. 사람이 직접 탐색하기보다 에이전트가 쓰는 내부 상태. 해당 한계에서 LLM Wiki(읽기 가능한 위키)와 방향이 다름.

### 3-3. qmd (tobi/qmd) — 로컬 마크다운 검색엔진
- Karpathy가 "Optional: CLI tools"에서 직접 추천한 도구. 온디바이스 검색엔진 for 문서/지식베이스/회의록.
- 기능: **BM25 전문 검색 + 벡터 시맨틱 + LLM re-ranking**(하이브리드), 모두 로컬(node-llama-cpp GGUF). RRF(fusion), 스마트 청킹(마크다운 헤딩·코드블록 경계 인식, tree-sitter AST 청킹), 쿼리 확장(HyDE).
- 장점: CLI(LLM이 셸로 호출)·MCP 서버(네이티브 툴) 양쪽 지원. 로컬(프라이버시). sota 기법 추적.
- 단점: 순수 **검색** 도구일 뿐 위키 생성·유지는 안 함 — 위키의 **보조 인프라**.

### 3-4. Obsidian AI 플러그인 (Smart Connections, Copilot, Text Generator 등)
- Smart Connections: 벡터 임베딩 기반으로 유사 노트 추천/연결.
- Text Generator / Copilot: LLM으로 텍스트 생성·요약·Q&A를 노트 안에서.
- 장점: Obsidian 생태계 안에 통합, 로컬, 노트 기반.
- 단점: 플러그인별 산발적 기능, **전체 위키를 체계적으로 유지하는 "관리자" 역할은 없음**(보통 단일 노트 대상). LLM Wiki는 이 "전체 유지"를 스키마+에이전트로 체계화.

### 3-5. 일반 RAG 시스템 (ChatGPT 업로드, 기타 RAG)
- 임베딩 저장소 + 쿼리 시 검색 + 합성.
- 장점: 구현 단순, 어디서나.
- 단점: 축적 없음, 요약·연결·모순 관리를 못 함. LLM Wiki의 대척점.

### 3-6. 기타 메모리/세컨드 브레인 계열
- **Letta/MemGPT**: 에이전트에 계층적 메모리(핵심/아카이브) 부여 — 에이전트 특화.
- **Khoj**: 개인 문서·메모에 대한 로컬 AI 검색/채팅(오픈소스, 자체호스팅).
- 공통: 대부분 **검색·채팅 인터페이스**에 집중. "에이전트가 영속 문서를 만들고 편집한다"는 LLM Wiki의 전략은 상대적으로 드묾.

## 4. gist 커뮤니티 논의에서 나온 개선/심화 아이디어

> Karpathy 포스트에 스타·포크 각 5,000+, 커뮤니티가 실무 적용에서 도출한 고급 패턴.

- **"gardener(정원사)" 패턴**: 위키의 캐넌(canon, 정본)을 유지하는 정원사와, 제안만 하는 라이브러리언 같은 역할 분리. 캐넌 결정(어떤 것이 정본을 수정하는가)은 인간에게.
- **ADR(Architecture Decision Records)**: 위키 구조 변경을 코드의 ADR처럼 문서화해 "왜 이 규칙인가"를 남기고 재조직을 방지. 댓글에 빌드까지 포함한 구현 사례 등장.
- **canonical vs derived(정본 vs 파생) 구분**:
  - **재도출 가능(derived/re-derivable)** 콘텐츠: LLM이 **자유롭게 자동 기록**해도 안전(파일 해시 vs 주장, 체크 exit code vs 주장 등 — 모델 없는 사실).
  - **비가역적(irreversible) 쓰기 / 사람에 대한 주장**: 반드시 **인간 승인 게이팅** 필요.
- **쓰기 규칙(write rules)** 제안: "재도출 가능한 쓰기는 자유 / 되돌릴 수 있는 쓰기는 제안 / 되돌릴 수 없거나 사람을 주장하면 절대 게이트" → 엄격한 "모든 연산은 제안만, 아무도 쓰지 않는다"보다 균형.
- **모순(contradiction) 처리의 이원화**: 모델이 "두 산문 주장이 동시에 성립할 수 없다"고 추론한 모순은 **위키에 하드코딩하지 말고 인간에게 보고**해야 함(모델의 추론이 기판에 박히는 것 방지). 반면 재계산 가능한 모순(파일 vs 해시)은 안전하게 구체화.
- **공개 위키 모델**: 개인판 Tolkien Gateway처럼 수천 페이지를 만들 수 있음 — 상호연결된 페이지(캐릭터/장소/사건/언어)의 커뮤니티 위키를 개인 독서 중에도 구축 가능.

## 6. 장점 취합 → 개인 문서 정리 설계 제안

각 방법론/툴의 **재사용할 장점만 뽑아** LLM Wiki 골격 위에 얹는 설계.

### 채택할 장점 목록
| 출처 | 가져올 장점 |
|---|---|
| LLM Wiki | 3계층(불변 raw / LLM 소유 wiki / 스키마), index.md+log.md, ingest/query/lint, 답변을 페이지로 저장 |
| Zettelkasten | 원자적 페이지(원자성), 자기 언어 재작성, 연결 중심 성장 |
| PARA | 최상위를 목적 중심으로(Personal / Research / Reading / Team…) |
| Johnny.Decimal | (선택) 일부 영역에 안정 ID 부여 |
| 커뮤니티 | canonical/derived 구분, 쓰기 게이트 규칙, ADR, gardener(인간 검토 루프), 모순 이원화 |
| qmd | 위키 성장 후 하이브리드 검색 도입(MCP/CLI) |
| Obsidian | graph view·Dataview·Marp·Web Clipper |
| Git | 버전 관리·되돌리기(LLM 무단 쓰기의 안전망) |

### 제안 폴더 구조 (스캐폴드)
```
~/notes/                        # 하나의 git repo
├── AGENTS.md                   # 스키마: LLM 워크플로우·규칙·쓰기 게이트
├── raw/                        # LAYER 1: 불변 소스 (LLM 읽기 전용)
│   ├── articles/
│   ├── books/
│   ├── podcasts/
│   └── assets/                 # 로컬 다운로드 이미지
├── wiki/                       # LAYER 2: LLM이 작성·유지
│   ├── index.md                # 카탈로그 (쿼리 진입점)
│   ├── log.md                  # 시간순 이벤트 (append-only)
│   ├── entities/               # 사람·회사·제품 등 엔티티 페이지
│   ├── concepts/               # 개념/주제 페이지
│   ├── sources/                # 소스별 요약 페이지
│   ├── synthesis/              # 종합·대조·비교 페이지
│   └── meta/                   # (선택) ADR·규칙 결정 기록
└── (캔버스/슬라이드 아웃풋은 별도 폴더)
```

### 스키마(AGENTS.md)에 기록할 핵심 규칙
1. **raw는 절대 수정 금지** — 위키만 쓴다.
2. **원자성**: 페이지 하나 = 개념/엔티티 하나. 너무 크면 쪼갠다.
3. **자기 언어**: 소스 요약은 내 언어로 재작성(복붙 금지), 인용은 raw 링크로.
4. **인덱스/로그 갱신**: 모든 ingest/query/lint 후 index.md, log.md 갱신.
5. **쓰기 게이트(canonical/derived)**:
   - 재도출 가능/되돌릴 수 있는 것(draft, 분류, 태그) → 자동 작성 OK.
   - 비가역적이거나 사람에 대한 주장(삭제, 개인 판단 서술) → **제안만 하고 승인 대기**(gardener 루프).
6. **모순 처리**: 두 산문 주장의 모순 → 보고만. 재계산 가능한 사실 불일치 → 위키에 기록.
7. **lint 주기**: 주기적으로 `lint` — 고아 페이지, 모순, 낡은 주장, 누락 개념 점검.

### ingest 워크플로우 예
```
사용자: [기사 URL/파일] 추가해줘
LLM: 1) Web Clipper/파일로 raw/ 로 저장 (불변)
     2) 원문 읽기
     3) 사용자와 핵심 포인트 토의 (선택)
     4) wiki/sources/ 요약 페이지 생성 (내 언어로)
     5) 관련 entities/concepts 페이지 갱신·크로스링크
     6) index.md, log.md 갱신
     7) 모순/갭이 보이면 lint 항목으로 기록
```

### 도입 로드맵(단계적)
1. **1단계 (베이스)**: git repo + raw/ + wiki/(index, log) + 스키마(AGENTS.md)만. LLM(Claude Code 또는 Codex)에게 이 문서를 주고 시작. 위키는 수백 페이지 넘어가기 전까지 **index.md만으로 충분** — 검색엔진 불필요.
2. **2단계 (성장)**: 위키가 커지면 **qmd** 추가(하이브리드 검색, MCP). Dataview frontmatter 도입.
3. **3단계 (심화)**: meta/ADR, gardener 검토 프로세스, Marp 슬라이드/차트 출력, 자동화 스크립트.

### 저장소 네이밍
- 이 저장소는 단순 위키가 아니라 **"위키(산출물) + raw(원본 소스) + 스키마(설정)" 3계층이 묶인 구조**라, 순수 `wiki`라는 이름은 원본 소스까지 포함한다는 성격을 다 담지 못함.
- **이름을 읽는 대상별 관점**:
  - **Obsidian vault**: 폴더명이 그대로 vault명이 됨 → `wiki`는 "wiki vault"로 표시.
  - **LLM 에이전트(Codex/Claude Code)**: `AGENTS.md`/`CLAUDE.md`는 repo명과 무관하게 최상위에서 자동 발견되므로 **이름은 기능적으로 무관**.
  - **사람(본인)**: 매일 타이핑하는 git/터미널 경로 → **짧고 직관적**일수록 좋음.

| 이름 | 장점 | 단점 |
|---|---|---|
| **`notes`** | 짧고 범용적. 위키·일기·리서치·독서기록까지 확장 가능. 타이핑 쉬움 | "정리된 지식베이스"라는 성격은 덜 드러남 |
| **`wiki`** | 단순명료, 목적 명시 | raw 소스 포함 구조는 안 담김, 다소 제네릭 |
| **`vault`** | Obsidian 용어와 자연스럽게 연결 | 개인 문서엔 다소 어색 |
| **`kb`** | 정체성 명확(knowledge base) | 축약어라 직관성 약간 ↓ |
| **`second-brain`** | 개념 전달 명확 | 길고 트렌디한 억양 |

- **추천: `notes`**
  - **가장 단순·타이핑 짧음** — 매일 쓰는 경로라 실용적.
  - **미래 확장성**: 나중에 워크로그·일기·독서기록 등 위키가 아닌 콘텐츠가 들어와도 `notes`가 자연스럽게 담음. `wiki`는 위키 아닌 콘텐츠가 오면 이름이 어긋나기 시작.
  - **검색/정렬 용이**: 자주 쓰는 명사라 IDE·fzf 같은 툴에서 찾기 좋음.
- 단, "원본 소스까지 포함한 구조"를 명확히 하고 싶다면 `notes-wiki` 또는 `kb`, Obsidian vault로 바로 열고 위키 전용으로만 쓸 거면 `wiki`도 충분히 좋음.
- **실용 팁**: repo 내부 구조(raw/·wiki/·AGENTS.md가 명확히 구분)가 이름보다 더 중요. 이름은 **매일 타이핑할 때의 편함** 기준으로 선택.

## 7. 결론·권장사항
- **LLM Wiki는 "RAG를 생성물(persistent artifact)로 승격"** 시킨 패턴 — 개인 문서 정리에 가장 잘 맞는 프레임워크.
- 시작은 **작게**: 위키 전체를 설계하지 말고, raw + wiki(index/log) + 스키마로 시작해 스키마를 사용자와 함께 진화.
- **Zettelkasten의 원자성·연결 원칙**과 **PARA의 목적 기반 폴더**를 결합하고, **커뮤니티의 쓰기 게이트(canonical/derived)·ADR·공개 위키 모델**을 보강해 안전망을 만든다.
- **git이 핵심 안전망**: LLM이 아무리 잘못 써도 되돌릴 수 있음 → 자동화의 부담을 낮춤.
- 데이터/프라이버시 중요하면 **로컬 우선**(qmd·로컬 마크다운·git) 선택이 유리.
